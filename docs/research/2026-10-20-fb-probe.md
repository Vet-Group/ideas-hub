## Payloads (observed 2026-10-20)

- The search document answers HTTP 403 and still renders through client JavaScript, as on 2026-10-19.
- Right after the load, the page navigates once on the client: the URL gains
  `sort_data[mode]=total_impressions&sort_data[direction]=desc`. Anything that evaluates in the page
  while that happens fails with "Execution context was destroyed".
- Embedded data: one `<script>` holding JSON (`require` → `ScheduledServerJS` →
  `RelayPrefetchedStreamCache` → `__bbox.result.data`). `data` has `ad_library_main`,
  `xfb_ad_library_is_captcha_required` (false in every search so far), `ad_library_system_status`,
  `ad_library_user` (null, logged out) and `page`. The connection is
  `ad_library_main.search_results_connection` with `count`, `edges` and `page_info`
  (`has_next_page`, `end_cursor`); ads are `edges[].node.collated_results[]`.
- `AdLibrarySearchPaginationQuery` responses (after an optional `for (;;);` prefix) have the same
  connection under `data.ad_library_main`, without `count`.
- No session tokens (`lsd`, `fb_dtsg`, user or actor ids, client IP) appear in either payload. The
  fixtures drop only `extensions` (a prefetch list of signed profile-picture URLs).

### Answers to the two Step 1 assumptions

1. **Has-next signal: present.** The embedded connection carries `page_info.has_next_page` and a
   total `count` (50001 for "more than 50,000", 0 for no results), and every scroll page carries
   `page_info`. AC 2 stands as written; no revision is needed before Step 3. Repeats and 2-page stops:
   see the sample tables.
2. **Thumbnail expiry: the URLs carry an expiry parameter.** Every fbcdn URL has `oe=<hex Unix
   seconds>`, about 4 days after the read (URLs read on 2026-10-20 expire on 2026-10-24). The 24 h and
   72 h re-fetches check whether they still load before that; a re-fetch after `oe` is expected to
   fail, which supports downloading thumbnails at capture time (spec §2).

### "No results" marker

A query with no ads returns the embedded connection with `count: 0`, `edges: []` and
`has_next_page: false`, and the page shows "No ads match your search criteria". The probe, and the
Step 3 detector, treat `count: 0` with no edges as `no_results`; empty edges with a non-zero count is
"embedded data empty without the marker", a block.

### The two "other" retries in the first smoke test

The first smoke search ("custom t-shirt", US) took 3 attempts. Attempts 1 and 2 failed with
`page.evaluate: Execution context was destroyed, most likely because of a navigation`: the probe
polled the page's scripts for the embedded data while the client-side `sort_data` navigation above
replaced the document. The error matched the transient pattern ("Execution context was destroyed"),
so the probe retried after 5 s and 15 s with a browser restart each time, and recorded it under the
catch-all kind `other` because it was neither a page-load, embedded-data nor scroll timeout. It was a
probe bug, not a network error or a block. The fix keeps polling when that error comes up during the
embedded-data wait; the next smoke run took 1 attempt per search. For Step 3: the adapter must wait
through this navigation, and "a navigation that destroyed the page context" (spec §1 "Transient
errors") should count only when it happens outside that expected redirect.

### What the sample shows

- **No block in any mode**: no captcha flag, login wall, empty embedded data or empty scroll payload,
  so the backoff never fired and no run stopped. 122 searches is a small sample; the twice-daily runs
  below test the chosen mode at the production rhythm.
- **Transient errors**: headed none; off-screen 3 searches with one scroll response that did not
  arrive within 15 s, each read on its second attempt; headless 6 such timeouts in 5 searches, and two
  searches ended as `parse_error` because the embedded `<script>` was read while still streaming
  (`SyntaxError: Unterminated string in JSON`), once on a retry after a scroll timeout. No timeout came
  with a block sign in the same run, so the `network_error` rule (a network streak of 3 is a 10 min
  cool-down, not a block) stands as written.
- **Repeats and the 2-page rule**: no scroll page repeated an ad already read, and no search stopped by
  the 2-page rule; all 118 `ok` searches stopped at the 100-ad cap after 7 scroll pages. A 2-page
  stop with a next page left therefore stays **neutral** (spec §1 "Backoff") and is still counted per
  run, so the Step 4 measurement can revisit it.

### Production browser mode: off-screen

Chosen: **headed with the window off-screen** (`--window-position=-32000,-32000` and the three
anti-throttling flags). Blocks seen: 0 in every mode, so the choice rests on the other evidence:

1. It is the real headed browser (no headless fingerprint), the safer default for a site that blocks
   automation, and it puts no window in front of whoever uses the PC during the 13:00 run.
2. Its 3 scroll timeouts in 40 searches were all recovered by the retry rule (5 s and 15 s waits, a
   browser restart), with no lost search.
3. Headless had twice as many scroll timeouts and the only two failed searches of the sample (the
   truncated embedded script). The Step 3 adapter now polls the script until it parses, but headless
   stays the last resort, for a host without a desktop session (the Linux trial, Step 8).
4. Headed is the fallback if off-screen retries grow in the twice-daily runs.

The worker reads the mode from `IDEAS_HUB_BROWSER_MODE` (default `offscreen`).

### Run-time estimate, measured

The spec §1 estimate assumed 5 s per page load and 1.5 s per scroll response. Measured over the three
modes: page load p50 1.4–1.6 s and p95 2.2–2.9 s; scroll response p50 about 1.0 s and p95 1.6–2.0 s
(the largest 3.6 s). A search to 100 ads took 19–21 s at p50, plus the 20–60 s gap: about 61 s per
search at mean delays; the headed run did 41 searches in 40 min. 160 searches at mean delays: about
2 h 43 min (the spec assumed 2 h 55 min). At the longest delays and p95 times (60 s gap, 1.3 s page
delay, 7 × 1.7 s scroll delays, 2.9 s load, 1.9 s embedded wait, 7 × 2.0 s scrolls): about 92 s per
search, 4 h 5 min for 160, inside the 4 h 30 min deadline with about 25 min left. Spec §1's estimate is
updated with these numbers.

### Wait limits and backoff

- Wait limits are kept: page load 60 s (p95 2.9 s), embedded data 15 s (p95 1.9 s), scroll response
  15 s (largest answered 3.6 s). The 15 s scroll limit was hit 9 times; each hit was a response that
  never came (the retry then read the search), not a slow one, so a longer limit would only lengthen
  the wait, and a shorter one gains little, since the limits bound hangs and hits are rare.
- Backoff starting values are kept (45 s base, ±15% jitter, a streak of 3 or 6 blocked searches stop a
  run, 6 h cool-down): no block was seen, so there is nothing to tune them on. Step 4's measurement at
  the production schedule is the next check.
