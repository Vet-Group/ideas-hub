# ADR 0002: Data model

Status: accepted (2026-10-20)
Deciders: owner (through the approved plan, Step 2)

## Context

Spec §2 "Main entities" lists the phase 1 entities, their key fields and unique keys. Plan Step 2 turns
them into a Drizzle schema (`packages/db/src/schema/*.ts`) and a first migration
(`packages/db/migrations/0000_init.sql`). This ADR records the choices the spec leaves open.

## Decision

- **Tables** (23, snake_case, plural): `users`, `stores`, `store_members`, `keywords`, `store_keywords`,
  `crawl_runs`, `crawl_searches`, `run_time_changes`, `keyword_days`, `shop_days`, `crawler_state`,
  `ads`, `ad_sightings`, `shops`, `news_feeds`, `news_items`, `holidays`, `briefings`, `suggestions`,
  `lark_messages`, `alerts`, `saved_ideas`, `settings`.
- **Keys**: text primary keys holding prefixed nanoids (`user_`, `store_`, `kw_`, `run_`, `srch_`,
  `rtc_`, `feed_`, `news_`, `hol_`, `brf_`, `sug_`, `lark_`, `alert_`, `idea_`), set by the app. Natural
  keys where the source gives one: `ads.ad_archive_id`, `shops.landing_domain`, `settings.key`.
  Composite primary keys for link and snapshot tables (`store_members`, `store_keywords`,
  `ad_sightings`, `keyword_days`, `shop_days`).
- **Times**: every timestamp is `timestamptz` (UTC). Pacific dates (`start_date`, `end_date`, crawl
  days) are `date`. A slot is the run's `scheduled_for`; `deltaAt` in `packages/core` matches slots by
  their Asia/Ho_Chi_Minh time of day, so a change of run times starts a new slot.
- **Fixed value sets** are `text` columns with `CHECK ... in (...)` constraints, not Postgres enums,
  because adding a value to an enum type is a one-way migration. The value lists live in the schema,
  except search statuses and roles, which `packages/core` owns and the schema imports.
- **Unique keys from spec §2**, as Postgres indexes:
  - `crawl_runs`: unique (source, `scheduled_for`) where `trigger = 'schedule'` (the target of the
    scheduler's and watchdog's `ON CONFLICT DO NOTHING`); unique (source) where `trigger` is `manual`
    or `cli` and status is `scheduled` or `running`. A check ties `scheduled_for` to scheduled rows and
    `requested_pairs` to manual and `cli` rows.
  - `crawl_searches`: unique (run, keyword, country), one row per planned search.
  - `ad_sightings`: primary key (ad, run, keyword, country).
  - `saved_ideas`: unique (store, source, `source_ref`) with default `NULLS DISTINCT`, so an image-only
    manual idea (`source_ref` null) is never deduplicated.
  - `briefings`: unique (date, scope, keyword) `NULLS NOT DISTINCT`, so there is one global briefing
    per date; a check ties `keyword_id` to `scope = 'keyword'`.
  - `lark_messages`: unique (briefing, chat) and unique `uuid`.
  - `alerts` dedupe: one per (run, kind) for `blocked`, `parse_error`, `missed_run` and `run_failed`;
    one per (run, `cooldown_seq`) for `network_error`, `cooldown_seq` being the run's
    `network_cooldowns` value after the increment written in the same transaction; one open
    `heartbeat_lost` (`resolved_at` null); one per (briefing, kind) for `briefing_late` and
    `lark_send_failed`.
  - `keywords.text` and `users.email` are unique case-insensitively (`lower(...)`).
- **Permissions**: `store_members` has three booleans (`can_view`, `can_save`, `can_keywords`).
  The rule that `save` and `keywords` imply `view` is applied once, in `packages/core/src/access.ts`,
  not by a constraint, so a tick set is stored as the admin ticked it.
- **Settings**: one row per setting (`key` text, `value` jsonb). The keys and defaults are
  `DEFAULT_SETTINGS` in `packages/core/src/settings.ts`; the first migration inserts the same values,
  and `packages/db/src/migration.test.ts` checks that the two agree. Validation of a settings change
  (spec §1 rejections) belongs to the code that writes them, not to the table.
- **Singletons**: `crawler_state` has one row (`id = 1`, enforced by a check), created by the first
  migration. Its `rotation_cursor` is jsonb until the Step 3 adapter fixes its shape.
- **First migration**: creates `pg_trgm` and GIN trigram indexes (`gin_trgm_ops`) on `ads.caption`,
  `ads.page_name` and `ads.landing_domain` for the Ctrl+K search; seeds the default settings, the first
  `run_time_changes` row (default run times, effective from install) and the `crawler_state` row. It is
  generated by `drizzle-kit generate` and then extended by hand with the extension and the seeds; later
  migrations are generated from the schema. `pnpm db:migrate` runs `drizzle-kit migrate`.
- **Users**: the `users` table carries the spec fields (email, name, role, disabled) plus the columns
  better-auth's user model needs (`email_verified`, `image`, `created_at`, `updated_at`), with
  better-auth's field names in the Drizzle schema. better-auth's `session`, `account` and
  `verification` tables are added by Step 5 in their own migration.
- **Deletes**: store-scoped and child rows cascade from their store, run or briefing; references to a
  user are set to null where the row outlives the user (`triggered_by`, `changed_by`, `assignee_id`),
  except `saved_ideas.created_by`, which blocks deleting a user who saved ideas (users are disabled,
  not deleted).

## Consequences

- Adding an enum-like value is a migration that replaces one check constraint.
- Settings are read as a whole object and typed by `Settings` in `packages/core`; a new setting needs a
  default there and a seed row in a migration.
- Sightings are kept 180 days (spec §2); the counts on `ads` stay. The purge job comes with the worker.
